# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ChimengSoso.github.io` — a GitHub Pages user site (deploys from the repo root, no `base` path needed), built entirely with Astro. It has two page groups sharing one site-wide navigation experience via Astro's `<ClientRouter />` (View Transitions):
- The home page (`src/pages/index.astro`) — a personal profile/link-hub with an interactive canvas starfield background (`src/components/StarfieldBackground.astro`).
- A Thai-language "knowledge" article section under `/knowledge` (`src/layouts/Layout.astro` + `src/pages/knowledge/*.astro`).

`public/` still holds static assets copied verbatim into the build output (`img.jpg`, `favicon.svg`, `promptpay-qr.png`, `robots.txt`, `knowledge/*` images) — but no longer any HTML/CSS of its own; there is no legacy static page bypassing the Astro build.

The planned feature backlog lives in **`docs/ROADMAP.md`** — when asked to "do the next feature" (or similar), pick from there, follow its per-item steps and verify/dependency rules, and tick its checkbox (+ note the commit hash) when done.

## Commands

- `npm run dev` — start Astro dev server (default port 4321)
- `npm run build` — build static site to `dist/`
- `npm run preview` — preview the production build locally
- `npm run check` — run `astro check` (full TypeScript type-check across `.astro`/`.ts`, incl. `<script>` blocks) — this is what catches the type errors the editor shows but `astro build` doesn't
- `npm run lint` — run ESLint (flat config in `eslint.config.js`: `typescript-eslint` + `eslint-plugin-astro`; `eslint . --fix` autofixes)

There is no test suite. **`astro build` does NOT type-check** — it compiles and can ship type-broken code. `npm run check` is the type gate and `npm run lint` the style/`any` gate, but **neither is wired into the build or the deploy workflow** (`.github/workflows/deploy.yml` only runs `astro build`), so they won't fail a deploy — run both manually before merging to `master`. After a non-trivial TS change, run `npm run check`: it surfaces the same errors the editor (WebStorm) shows, all at once, instead of finding them one screenshot at a time. `tsconfig.json` extends `astro/tsconfigs/strict` and excludes `eslint.config.js` (no point type-checking the lint config against the app config).

## Branching & deployment

- `master` is the default/production branch (**not** `main`) — only `master` triggers deployment. Do routine work on `develop` and merge into `master` when ready to publish; this is intentional, so pushes to `develop` don't go live.
- Pushing to `master` triggers `.github/workflows/deploy.yml`, which runs `withastro/action@v6` (installs deps, runs `astro build`) and deploys `dist/` to GitHub Pages via `actions/deploy-pages@v5`. There is no separate staging environment — every push to `master` goes live immediately.
- The repo's GitHub Pages source is set to **"GitHub Actions"** (not the legacy branch-based Pages source), so deployment only happens through this workflow. If the workflow's `on.push.branches` trigger is ever changed, remember `master` is the branch that matters here, not `main`.

## Commit messages

This repo's history is strictly single-line, imperative-mood, no body (e.g. `Add interactive starfield background and handle scramble effect`, `Fix profile page bugs and accessibility issues`). Don't add a bullet-point body or a `Why:` explanation paragraph — match the existing terse style. Only commit when the user explicitly asks (`commit ได้เลย` or similar); don't commit proactively after finishing a task.

## Adding a new article

Always touch two places:
1. Create the new `.astro` file in `src/pages/knowledge/`, using `<Layout>` the same way `claude-intro.astro` does. In the frontmatter: call `getArticle(href)` from `src/data/articles.ts` and `formatThaiDate` from `src/lib/dates`, derive `published`/`updated` strings, then pass them to `<ArticleByline>` (Layout no longer takes an `updated` prop — the byline renders the date itself) — no hand-written Thai date strings in the page file. Pass `title={\`${article.title} | หมวดความรู้\`}` and `description={article.desc}` to `<Layout>` — like the date, title/description derive from `articles.ts` rather than being hand-typed again in the page (this is the single source of truth for what the listing card, RSS, and OG image show too). Pass `headline={article.title}` so the `BlogPosting` JSON-LD headline stays suffix-free. Pass `prev`/`next` from `getAdjacentArticles(href)`. If the title contains slash-command tokens (e.g. `/grill-me`), wrap them in `<code>` in **both** the breadcrumb and the `<h1>` so they render as chips (see the slash-command-chip bullet in Architecture notes) — the breadcrumb/`<h1>` are still hand-written since they need this manual wrapping.
2. Add its entry in the `articles` array in `src/data/articles.ts` (typed `Article[]` — a missing/mistyped field now fails type-check in-editor), setting `soon: false`, `href` pointing at the new file in directory-style form (e.g. `my-article/`, not `my-article.html` — see the directory-style build note below), plus `dateISO` (YYYY-MM-DD publish date, e.g. `"2026-07-09"`) and `readingMinutes` (integer estimate — the listing shows both). Set `updatedISO` only when the article is later revised. Order in the array determines prev/next link order and reading order on the listing page — insert it where it should sit in the sequence. To estimate `readingMinutes`, count the Thai characters in the article body (a decent prose proxy — strip tags/`<style>`/`<script>`/code) and divide by ~1000–1100; it's shown as "อ่าน N นาที" and is easy to tweak by hand later.

The article's Open Graph share image is generated automatically — do **not** set an `image` prop or add a screenshot asset for it. `Layout.astro` derives `og:image` from the page URL and `src/pages/og/[slug].png.ts` renders a branded card from the entry's `title`/`tag` (see the Open Graph bullet in Architecture notes).

**Everything else derives automatically from those two touches — do NOT hand-edit any of it:** the `/knowledge` listing card + its topic-section grouping and per-section count (grouped by `tag`, first-seen order — **reuse an existing tag** unless the owner wants a whole new section heading), the meta row ("อ่าน N นาที" + short date), prev/next links on the *neighboring* articles (they re-derive; don't touch their files), the RSS item in `/rss.xml`, the OG PNG at `/og/<slug>.png`, the sitemap entry, `BlogPosting` JSON-LD + `article:*_time` metas, and the sticky TOC (auto-built from the page's `h2`s — so structure the body with `h2` sections). No privacy-policy change is needed for a plain article (no new storage/third-party requests).

**Article body building blocks** (all styled globally in `Layout.astro` — see `claude-intro.astro` / `ai-taste.astro` for usage): `<div class="callout callout-tip">`/`callout-note` with a `<p class="callout-label">` heading, `card`, `step`, `diagram`, `divider`/`divider-solid`, `expander`+`expander-body`, `pull` (pull-quote), and a final `<ol class="references">` for sources. Code samples use the `<CodeBlock>` component (copy button included), not bare `<pre>`. Images for the body go in `public/knowledge/` and are referenced as `/knowledge/<file>`; prefer local copies over hotlinks, with attribution in the caption/references.

**Writing style (the owner's signature — don't drop these):**
- Thai, friendly and "เข้าใจง่าย" — same voice as the existing six articles; read one before writing.
- **Gloss flagship English terms**: give the Thai transliteration (how to pronounce), a short Thai meaning, and — when it lands well — the word's origin, with a playful wink. Prototype: claude-intro's *Claude อ่านออกเสียงว่า "คลอด"* + the Claude Shannon origin. Format: `<strong>` around the pronunciation/meaning, `<i>` only around English example words (Thai in italics looks bad). A few per article on the key terms, not every word; proper nouns/people get glossed once at first mention in reading order. **Don't re-gloss terms already glossed in an earlier article** — grep the existing `src/pages/knowledge/*.astro` for the term first.
- **A gloss box must never be the first place an English term appears.** The owner calls this "เสร่อ": the prose says only the Thai word (`อนุพันธ์`, `ขนาดตามหน้าสัญญา`), then a gloss callout abruptly drills `Derivative` / `Notional size` the reader has never seen, so they can't tell which Thai word it maps to. Rule: **introduce the English in parentheses right after the Thai on first mention in the prose** (`อนุพันธ์ (derivative)`), and only then gloss it in detail. Same for **abbreviations** — bind them to the full term at first use (`Enterprise Value (ย่อว่า EV)`) before using the short form anywhere, including inside SVG diagram labels. And gloss where the term is actually *used*: don't drop a four-term gloss box before the sentence that needs those terms, or the reader meets the pronunciation before the word.
- Fact-check claims about AI products/models/dates before publishing (WebSearch) — the owner cares about accuracy and has caught errors before.

**Don't write like an AI (applies to ALL published prose — `/knowledge/*` AND `/divine-lore/*`, plus the `title`/`desc` strings in `articles.ts`/`divineLore.ts`).** The owner reads drafts specifically looking for these and has sent work back twice for it (commit `6096395` stripped every em-dash from the ICPC editorial; the `llm-cheese-types` draft came back with 64 of them). This is a *style* rule about the owner's voice, not about the source material — a source that overuses these still gets rewritten in the owner's voice.
- **Zero em-dashes (`—`) in article prose. This is a hard rule, not a budget.** Thai body text doesn't need them, and they are the single loudest AI tell. Grep the file before declaring done: `Grep pattern '—'` must return 0 hits in `src/pages/knowledge/*.astro`, `src/pages/divine-lore/*.astro`, and both data files. Replacements, in order of preference: (a) just a space — Thai reads fine without any connector; (b) split into a new sentence; (c) parentheses for a genuine aside or a heading label (`ท่าที่ 1 — ปิดเสียงเตือน` → `ท่าที่ 1: ปิดเสียงเตือน`, `แนวคิดที่ 1 — คิดตรง ๆ` → `แนวคิดที่ 1 (คิดตรง ๆ)`); (d) a colon when what follows really is an explanation. In `<figcaption>`, `<CodeBlock title>`, SVG `<text>` labels, and `<li>` lead-ins, use `·` or parentheses. Inside code strings, use a plain space in comments. **The rule is about prose, so it does not cover the `—` used as a "no value" glyph in a UI table cell** (`flow !== 0 ? signed(flow) : '—'`). `/games/nee-noo` and `/games/tax-gap` hold 17 of those and they are staying: em dash for a missing figure is the standard convention in a financial table, and swapping it changes rendered UI rather than voice. A grep over `src/pages/games/` therefore returns 17 by design. Classify before you replace: the only genuine violation found there was one `<li>` citation (`กรมสรรพากร — ผู้มีเงินได้...`), now a `·`.
- **No negative parallelism** (`ไม่ใช่ X แต่คือ Y`, `it's not X, it's Y`). AI reaches for this constantly. Say the positive claim directly: `AI ไม่ได้ปีนนั่งร้าน มันเดินอ้อมนั่งร้าน` → `AI ชอบเดินอ้อมนั่งร้านมากกว่าปีนขึ้นไป`. One is fine if it's genuinely the clearest phrasing; three in an article is a tell.
- **No grandiose closers on paragraphs** (`และนั่นคือใจความทั้งหมดของเรื่องนี้`, `นี่แหละคือหัวใจของเรื่อง`, `ทั้งหมดนี้สรุปได้ว่า`). End the paragraph on the last real piece of information and move on. Same for compulsive recap sentences at the end of a section that just restate the section.
- **Ration the bold.** Bolding a phrase in most sentences is a formatting tell and it stops meaning anything. Bold the term being defined and the one claim per section that must not be missed. Prose that reads well unbolded should stay unbolded.
- **Watch the rule of three.** Lists that always land on exactly three items, and triplets of adjectives, read as generated. If the source has four reasons, write four.
- **Don't dress up a paraphrase as a quotation.** A `class="pull"` pull-quote in quotation marks reads as the source's verbatim words. If it's your summary of their point, write it as attribution instead (`Justin อ่านพฤติกรรมพวกนี้ว่า...`), and reserve quote marks for text actually lifted from the source.

**Verify (new-article checklist):** `npm run check` + `npm run lint` + `npm run build`, then in the live preview: the listing shows the card in the right section with the right count and meta row; prev/next work on the new page **and** both neighbors; `/rss.xml` gained the item; `dist/og/<slug>.png` was generated and shows the title/tag correctly; `/` ↔ article client-side navigation still works (`astro:page-load` gotchas). Finally grep the new file for smuggled zero-width spaces (`\x{200B}`) **and for em-dashes (`—`, must be 0 — see "Don't write like an AI" above)**.

## Adding a competitive-programming problem (`/cp/`)

`/cp/` is a private-ish problem vault: **the only door is the `/divine-lore/` listing** (same arrangement as `/games/`), it is excluded from the sitemap (`astro.config.mjs`) and every page renders `noindex` via `DivineLoreLayout`. Unit is **one problem = one page**, grouped on the hub by contest/set.

Two touches per problem:
1. Add the entry to `cpProblems` in `src/data/cp.ts` (`href` directory-style, `setId` matching a `cpSets` entry, `label`, `title`, `desc`, `topics`, `difficulty` 1-5, `dateISO`, `readingMinutes`). If it belongs to a new contest, add the `CpSet` first. Array order = hub order and prev/next order.
2. Create `src/pages/cp/<slug>.astro` from `docs/cp-problem-template.astro.txt`, passing only `href` to `<CpProblemLayout>` — title, set pill, difficulty, topics, date, and prev/next all derive from `cp.ts`; never hand-type them in the page.

**Those two touches are the whole job. Everything else derives from the `cp.ts` entry and must NOT be hand-edited:** the hub card, the per-set group heading and its count, **every chip in the filter rail on `/cp/` (ชุด / หัวข้อ / ระดับ) and each chip's count**, the sort orderings, the OG PNG at `/og/cp/<slug>.png` (`src/pages/og/cp/[slug].png.ts`, emerald `divine` theme), the `og:`/`twitter:` meta (`DivineLoreLayout` branches on `/cp/`), prev/next on both neighbours, and the door card's count on `/divine-lore/`. Adding a new topic string is the only thing that needs a third touch, and it is a one-line one: see `CP_TOPICS` below.

**`topics` is a closed vocabulary, not free text.** `src/data/cp.ts` exports `CP_TOPICS` and types `topics: CpTopic[]`, so a typo (`'BFS'` for `'bfs'`, `'prefix-sum'` for `'prefix sum'`) is a **type error** in `npm run check`, with a "Did you mean" suggestion. This exists because topics became filter chips: two spellings of one topic silently become two chips that each filter half the vault. To introduce a genuinely new topic, add one line to `CP_TOPICS` — a deliberate act, which is the point.

**Four more invariants fail the build with a plain-language message, so you cannot ship them by accident.** `assertCpData()` in `src/data/cp.ts` runs on import (every `/cp/` page imports it, so `astro build` always executes it) and rejects: an `href` that is not lowercase-kebab ending in `/`; a duplicate `href`; a `setId` with no matching `cpSets` entry (which would make the card vanish from the hub silently); and an empty title/desc, empty or duplicated `topics`, a malformed `dateISO`, or a non-positive `readingMinutes`. Separately, `src/pages/cp/index.astro` cross-checks the `cp.ts` list against the actual `src/pages/cp/*.astro` files **in both directions**: an entry with no page file (a card that 404s) and a page file with no entry (an orphan with no card, no prev/next, no share image) each stop the build. `CpProblemLayout` already throws when a page's `href` prop matches no entry. So after adding a problem, `npm run build` alone tells you whether the wiring is complete.

Reading order per problem is the contest-article standard already documented below (story → spec callout → hint → optional playground → reveal): use `<Spoiler>` for anything that reads as the answer, and `<Spoiler linked>` (buttonless) for downstream spoiler-y blocks like a method-leaking `io-note` — one tap on the main button unlocks every `.spoiler` sibling until the next `<hr>`/`<h2>`. The blur CSS lives in `src/components/Spoiler.astro`, the toggler script and the `table.io`/`.spec`/`.io-note` CSS in `src/layouts/CpProblemLayout.astro` — don't copy them into a problem page. `src/pages/divine-lore/icpc-warmup-2026.astro` is the older all-problems-in-one-file page; leave it where it is.

**Getting a `programming.in.th` statement out.** `WebFetch` on `/tasks/<id>` returns only the SPA shell. Fetch `https://programming.in.th/api/tasks/<id>/statement` with `curl` (it is a PDF), then read it with `pymupdf`'s `page.get_text()` and write the result to a UTF-8 file. `pdftotext` mangles Thai; `pymupdf` does not. If the extracted Thai looks like `��ҧ��ý֡`, that is the Windows console's codepage, not the extraction: write to a file and read the file. Rendering pages to PNG (`page.get_pixmap`) is a fallback for figures, but never the first move, since 30-odd page images cost far more than the text.

**Lesson pages (not a contest problem).** `/cp/` also holds teaching articles. Same two touches, with `kind: 'lesson'` on the `cp.ts` entry and `setId: 'basics'`; the layout then renders a "บทปูพื้นฐาน" chip and retitles the star tooltip to "ระดับเนื้อหา", the hub prints the chip on the card and counts the group in บท instead of ข้อ. Everything else (OG card, noindex, prev/next, sitemap exclusion) is identical. A lesson still follows the reveal-after-hint rule: its practice problems each get story → spec callout → hint callout → `<Spoiler>` reveal, and the reveal ships stress-tested code like any problem page. Reference: `src/pages/cp/interval-dp.astro`.

### Standards every `/cp/` page follows (set by `pick-books.astro` — copy them, don't re-derive)

**Numbers and code**
- **Formulas are code windows, not blackboard math.** `/cp/*` renders every KaTeX display with `texCode()` + the `mc` helpers from `src/lib/math.ts`, which paint it in the exact shiki **dracula** palette the page’s code blocks use (table/array/function names `#50FA7B`, numbers `#BD93F9`, operators `#FF79C6`, bare index variables left at the base `#f8f8f2` — shiki leaves scalar locals unpainted too), on the same `#282a36` background via `.mathblock.mathcode` in `CpProblemLayout`. Two traps: KaTeX cannot take these colours as **macros** (its parser reads the `#5` in `#50FA7B` as macro parameter 5 and throws), so `	extcolor` is written out by the `mc` helpers; and `	extcolor{…}{\max}` turns `\max` into an ord, which moves the condition from under it to beside it — use `mc.max` (`\mathop{…}\limits`) instead. Do not colour by meaning (one colour per branch of the recurrence): that was tried and reads as decoration, and it fights the code windows next to it.
- **Every DP recurrence gets a meaning-first translation, one bullet per branch, placed between the formula and the summary table.** A displayed formula speaks in table indices while the state definition speaks in the problem's own nouns, and nothing bridges them; the owner read `/cp/pick-books`'s recurrence and said the definition was clear but the formula made him lose it. The shape that worked, in this order: (1) one **anchor sentence** naming what the indices mean relative to the decision (`p` = the count *after* deciding this item, the source cell's index = the count *before*), so the reader can re-derive `p-1`, `p+2`, `0` instead of memorising them; (2) **one bullet per branch**, each reading decision -> what the count was before -> why the arithmetic lands on `p` -> what happens to the score -> when the branch is unavailable; (3) one closing line on the **consequence**, e.g. that column `p = 0` has only two ways in. Then the existing table demotes to a scan-it summary. Rules learned while drafting it: state the guard as a **positive fact** ("the item that just became a plus is itself one pending plus, so after deciding there is always at least one"), never as proof by contradiction ("suppose p = 0 ... that contradicts ..."), which makes the reader hold a counterfactual for no gain; keep the index-level reason (`dp[i-1][-1]` is off the table) out of the prose and put it in the table's condition column, because prose is where meaning lives and the table is where index guards live; and reuse the exact vocabulary the page already established earlier (here "ผลักเข้าสแต็ก" / "บวกค้าง") so the bullet reads as the same sentence in a new context rather than a new reason. Reference: the passage under the RECURRENCE formula in `src/pages/cp/pick-books.astro`.
- **Pick one direction for the recurrence and use it everywhere.** The table, the step players, and the shipped code all read the DP the same way: **pull** (stand on the destination cell `nxt[q]`, ask which sources point into it), because reading a DP table by eye is a pull. The mirror form (push: stand on `cur[p]`, fan out to `nxt[p+1]/nxt[0]/nxt[p-2]`) is worth showing, but as an optional expander at the end of the section, never as a bridge the reader must cross to reach the code. Switching direction midway is what made `/cp/pick-books` confusing enough for the owner to ask about it.
- **Every figure comes from a model in the frontmatter, never typed by hand**: the DP table, the step-by-step script of each player, the cost table, and the numbers interpolated into prose all derive from the same functions. A hand-typed number that contradicts the table then cannot happen, and `npm run check` type-checks the model.
- **Stress-test the shipped code before publishing.** Extract the C++ out of the page, compile it, and race it against a brute force on a few hundred random small inputs plus every sample in the statement. Do this for *every* code block the page ships, including the "wrong way" one. Only claim a round count in the prose if you actually ran it.
- Ship a second expander with the brute-force checker: it teaches the stress-test habit and it is the thing that made the main claim trustworthy.
- **Ship the full-constraint solution, and every subtask's solution on top of it.** A partial-credit answer is not the deliverable: `/cp/archery` first shipped an `O(N³)` that only reached the 20-point subtest, and the owner came back with "เฉลยข้อ archery ต่อเอาให้ครบ sol <= 200000". When the statement lists subtasks, each one gets its own explained angle *and* its own compiled, stress-tested code, because they are the cheapest cross-checks available and they are what "เน้นฝึกให้คิดหลากหลายมุม" asks for. Say plainly which subtest each code block wins, and if something genuinely cannot be reached, say that instead of implying it can.
- **Passing the statement's own samples is not evidence of anything.** Four bugs in one batch passed every sample in their problem: Teleporters' greedy (leftover machines scored `+2` each instead of `+1` then `+3`), Pyramid Base's segment tree (padding leaves left at 0, so the global minimum was always 0), and two in Archery (the flow formula going negative while target 1 held no strong archer, and assuming `u(k)` crosses a multiple of `N` at most once). Every one was caught only by a random cross-check. Samples are written to explain the problem, not to break solutions; budget for the checker before you budget for the solution.
- **When the page's correctness rests on a characterization, the checker must not use that characterization.** Training's checker enumerates every simple cycle and tests its parity instead of trusting "cut the odd-path roads, keep an edge-disjoint set of even ones"; Flood's grid flood-fill is an independent model of the planar face graph; Fish's brute force collects reachable jewel multisets in a `set` with no dedup theory at all. A checker that shares the solution's central assumption only tests the typing.
- **Every solution section carries how the idea was found, not just what it is.** The owner read the first sixteen pages and said `เธอเล่นเฉลยเฉย ๆ ... วิธีคิดพวกทำไมถึงคิดแบบนี้ เธอลองอะไรมาถึงมั่นใจว่าใช้แนวคิดนี้ได้ ... เธอไม่เล่าตรงนี้เลย`. The approved shape (three pages already done: `archery`, `teleporters`, `sails`) is a callout as the **first child inside the section's `<Spoiler>`** — it is part of the reveal, so it must not sit outside one. Labels in use: `ที่มาของแนวคิดนี้` (`callout-note`, when there is no failure to tell, so tell the pressure that forced the idea instead), `สองทางที่ผมลองก่อน แล้วทิ้ง` (the alternatives you priced and rejected, with the number that killed each), `ที่มา และสามรอบที่ยังผิด` (with a table of how many points were still wrong per attempt), `เรื่องจริงที่เกิดขึ้นตามลำดับ` and `ผมแก้ถูกตั้งแต่แรก แต่เข้าใจเหตุผลผิดอยู่นาน` (both `callout-warn`, for a bug that passed the statement's samples, or a fix that was right for the wrong reason). Rules: tell it in the order it actually happened, not the tidy order; give the number that drove each decision (`คูณออกมาแล้วยังหมื่นล้าน` beats `มันช้าเกินไป`); close with one sentence of transferable lesson; and **never invent a failure that did not happen** (see the memory `no-overclaiming`). Two to four paragraphs per callout.
- **A structural claim the prose makes should be re-checked at build time.** `/cp/archery` derives the steady state (rank 1 parked at target 1, ranks 2..N+1 circulating, the rest frozen) from a real simulation in the frontmatter and prints "ตรงตามข้ออ้างทั้งสองชุด" or "ไม่ตรง" in the figcaption, so a broken claim announces itself instead of quietly lying in the prose.
- Solution code is competitive-style but readable, Thai comments, and **no dead knobs** — `int lim = min(i, n - 1)` where `i ≤ n-1` always was shipped once; a careful reader stops to ask why, so write `p <= i` and say why in a comment.
- **One unit per comparison.** If a table compares two approaches' time/memory, count both with the same bytes-per-cell as the code actually shown on the page, and say so in the cells. A second unit is allowed only as an explicit "most generous case for the loser" sentence.

**Layout (`CpProblemLayout`)**
- One centred axis: text at `46rem`, blocks (`figure.tbl`, `.dpsim`, `.mathblock`, `.code-window`) at `width:fit-content` under a `66rem` ceiling, diagrams and `.bookgame` at `52rem`, all centred. At `min-width:72rem` the card itself is `width:fit-content` so it hugs the widest block plus its own padding instead of leaving dead background either side.
- **The Thai `max-content` trap, the single biggest source of layout bugs here.** Thai has no inter-word spaces, so a paragraph's `max-content` is the whole sentence on one line. Any Thai text inside a `fit-content` box therefore *sets that box's width*, and if the text changes (a step player's explanation) the box resizes on every step. Two places already bitten: `.dps-say` (players resized 769px↔1246px per step) and `figcaption` (cards ended up wider than their own table, reading as a notch — COST was 155px off). The fix for both is `width:0; min-width:100%`: the block stops contributing to intrinsic width but still renders full width, so long text becomes extra *height*, which is what a player wants. Apply it to any new Thai caption or panel inside a shrink-to-fit box. A **table cell** cannot take the trick directly (a `td` with `width:0` is ignored by the table layout, and `overflow-wrap:anywhere` does not help because `fit-content` sizes from *max*-content): put the label text in an inner `<span>` and give the span `display:block; width:0; min-width:100%`. This bit the rollsim row labels, whose per-step text (`nxt = dp[0] (แถวเก่า รอถูกทับ)` vs `nxt (ยังไม่ใช้)`) moved the whole player 815px↔824px.
- **Two more things that resize a `fit-content` card between steps, both found by measuring every step at ≥1280px.** (a) The step counter (`.dps-count`, `white-space:nowrap`) grows when the number goes from one digit to two, which widened the whole player by 8px at step 10 of 11; give it a `min-width` that already covers the widest string it will ever hold. (b) A grid whose cells gain content or `font-weight:700` as they fill re-measures its columns; put `table-layout:fixed` on it with an explicit `width` on the label column and the value columns, and keep the table at `width:auto` so it still hugs those columns instead of stretching to the card. Note `width:100%` + `table-layout:fixed` does the opposite: the card loses its content-based width and balloons to the `66rem` ceiling.
- **A new block class is invisible to the centring rules until you add it to them by name, and nothing errors when you forget.** The `/cp/` centring rules are hard-coded selector *lists* (`figure.diagram`, `.bookgame`, `hr.divider`, `p`, `ul`, …), not a catch-all. Every class a new page invents (`.plategame`, `p.io-note`'s card, `hr.divider-solid`) therefore falls out of the list and silently renders at full card width while the text column stays centred, so the page reads as "everything is shifted left". `/cp/interval-dp` shipped five of these at once. Two matching traps: a page-level `margin:1.4rem 0` **overrides the layout's `margin-left/right:auto`** (scoped page styles carry an extra attribute selector, so they win) and pushed `p.pull` 98px off-axis; and a caption written as a sibling `<p class="io-note">` is sized by the *article* column (1032px) while the player it describes is 700px, so it overhangs by 167px on each side. Rules: when you add a block class, add it to both layout lists in the same edit; never write a shorthand `margin` with `0` on a block the layout centres; keep a player's or game's caption **inside** its card. **The check that catches all of them in one pass** (run it before calling a `/cp/` page done): walk `.panel`'s children and print `left - panel.left` vs `panel.right - right` for each; any row where the two differ is off-axis (only `p.tag`, the shrink-to-fit pill, is allowed to).
- **A `fit-content` card wants `width:0; min-width:100%` on the table too, not `width:100%`.** `.dpsim` is `width:fit-content`, so a table set to `width:100%` still hands its own max-content to the width calculation and the card ballooned from 698px to 1109px. The Thai-caption trick works here verbatim: `width:0; min-width:100%` with `table-layout:fixed` fills the card without contributing to it, which is what fixes the "table stops short of the card" notch (the table hugged its columns at 546px inside a 698px card set by the button bar). `figure.tbl` is the opposite case and keeps hugging.
- **A diagram's `viewBox` must be as wide as the drawing, not a round number.** Both diagrams on `/cp/interval-dp` used `0 0 720 …` while the real content ended at 512 and 573, leaving 20-29% dead space that reads as "the picture is shoved left" even though the block is perfectly centred. The thing that hides it is a full-width divider line inside the drawing, which makes the whole-SVG `getBBox()` look full; measure the *content*, not the SVG. Also **reserve an empty bottom-right band** roughly 50x30 user units (scaled): `ZoomableDiagram`'s "ขยาย" button floats over that corner and will sit on top of any label there. And never put explanatory prose inside the SVG: it lands in that corner, and it is left-aligned while every `figcaption` on the page is centred. Prose belongs in the `figcaption`; the SVG keeps only labels that point at something in the picture.
- **An edge label offset by a constant `x` will cross its own line on every diagonal edge.** `/cp/type-printer` labelled each trie edge at the midpoint plus `9` in x, which is clear for vertical edges and runs straight through the glyph for diagonal ones (four hits, found by sampling each `<line>` with `getPointAtLength` and testing the points against every `<text>`'s `getBBox()`). Offset along the edge's **normal** instead: `n = (dy, -dx)/len`, flipped so `nx ≥ 0`, times ~13 units. The tightening numbers that worked for the whole `/cp/` batch: `viewBox` width = content right edge **+ 12**, height = content bottom **+ 34**, which leaves exactly the empty bottom-right band the "ขยาย" button needs and nothing more.
- **Check drawn lines against text boxes numerically.** The pairing arc `M37 118 C 37 96, 281 96, 281 118` ran straight through the heading at y 93-112. Sample the path with `getPointAtLength` and compare against every `<text>`'s `getBBox()`; reading the coordinates in the source is not enough.
- **Table-cell highlight CSS needs `.num`.** `table.rec td.num` is specificity (0,4,2) and sets `color`; a rule written `.dpsim td.is-target` is (0,4,1) and loses, so the background lands but the text keeps the pale grey. Write `.dpsim td.num.is-target` (0,5,1). Same for every `is-*` state in both players.

**Step players (`.dpsim` / `.rollsim`)**
- Steps are built at build time into `data-steps`; the script only renders them. Init inside `astro:page-load` with a `data-wired` guard.
- **The explanation must never name a cell that is not on screen.** Rejected sources outside the rendered columns are described in words ("ช่องที่ค้างบวกไว้ 8 เล่ม ซึ่งมากกว่าจำนวนหนังสือทั้งกอง") instead of `dp[5][8]`, which a reader will hunt for and never find.
- Keep the active cell visible with a `keepInView` helper that nudges `.dps-scroll`'s `scrollLeft` directly. Not `scrollIntoView` (it drags the page vertically too) and not `behavior:'smooth'` (stepping is already discrete, and smooth animations queue up when the reader clicks fast or hits play).
- Controls are first/prev/play/next/last plus a range input, all driving one `render()`; `disabled` state is derived there too.

**Mini-game**
- The optimal score per pile is a hardcoded constant. Do **not** ship the solver to the page: the reveal below is the solver.
- The pile set earns its keep: the greedy trap, the statement's own samples, and the pile the walkthrough later uses.
- Nodes built in JS need `:global(...)` on their CSS (scoped styles never match them), and every animation needs a `prefers-reduced-motion` path.
- **A `figcaption` above the reveal must not spoil it.** "กอง D คือกองที่ต้องยอมเหลือหนังสือทิ้งไว้หนึ่งเล่ม" handed the reader the shape of the answer before they played; tease the pile instead.

**Every `/cp/` page carries a playable round, and they all share one chassis.** All 29 pages now open a `ลองเอง` block before the reveal, so the reader has tried the problem by hand before reading the answer (the reveal-after-hint rule applies to games too: the game sits above the `<h2>` it precedes, never inside the `<Spoiler>`). The shared parts live in two places and must not be re-invented per page: `src/lib/cpGame.ts` exports `cpGameUi(selector)` (tabs, status line with `good`/`bad`/`plain` tones, score line, tease line, `onClick(attr, cb)`) and `readPuzzles(root)` (parses `data-puzzles` and returns `unknown[]` so the page narrows it itself, never `any`); the card chrome (`.cpgame`, `.cpg-tabs`, `.cpg-tab`, `.cpg-tease`, `.cpg-status`, `.cpg-score`, `.cpg-hint`, `.cpg-controls`, `.cpg-btn`, `.cpg-btn.main`, `.cpg-scroll`, `.cpg-cap`) is defined once in `CpProblemLayout.astro`'s global style. A page adds only its own board markup, board CSS, and wiring. `.cpgame` is already registered in both centring lists; a new board class of your own still has to be added to them by name.

Rules the whole set follows, learned while building them:
- **The answer key is computed in the frontmatter, and by a method the page is not teaching.** `sails` brute-forces every arrangement, `teleporters` enumerates every way to spend the machines, `training-route`'s checker enumerates simple cycles instead of using the two rules the page derives, `islands` walks every simple path, `mobiles` tries all 2^axes flips. Several pages then **throw at build time** if the brute force disagrees with the page's own solution (`sails`, `teleporters`, `type-printer`, `mobiles`, `archery`, `fish-jewels`, `islands`, `training-route`, `flood-walls`), so a wrong game cannot ship. Prefer that over trusting the shipped solver.
- **A puzzle the player cannot win must be winnable another way.** `mobiles`, `killer-square`, `state-graph-bfs` and `trie` each include a case with no solution, and each gives a button to say so ("ชุดนี้ทำไม่ได้"). The `trie` case shipped once with no such button and no reachable answer, which is a dead end, not a lesson. Verify the impossible case is genuinely impossible: the first `mobiles` layout I picked turned out solvable in one swap, and the first two `flood-walls` layouts had zero surviving walls, which teaches nothing.
- **TypeScript does not narrow a `const` across a hoisted function declaration.** Every game hits this: after `if (!maybeUi) return;` bind `const ui: CpGameUi = maybeUi;` (and the same for each `querySelector` result) or every use inside the game's functions errors with `ts(18047)`. Do not reach for `!`.
- **Check for a name collision before adding a frontmatter helper.** `count-then-walk` already had `noAdjacentOnes` and `tree-dp` already had `subtreeSizes`; redeclaring them gave a lint error and a runtime `TypeError` respectively. Reuse the existing one or prefix yours (`gameSubtreeSizes`).
- **Insert frontmatter at the real fence, not the first `---` you find.** `state-graph-bfs` broke because a `/* ---------- ... */` banner comment matched first. Split on lines that are exactly `---`.
- Thai text inside the card (`.cpg-tease`, `.cpg-status`, `.cpg-score`, `.cpg-hint`) already carries `width:0; min-width:100%` for the `max-content` trap; any new Thai panel you add needs the same, and `.cpg-status` has a `min-height` so the card does not jump as the message length changes.
- **The dev server serves stale HTML after these edits more often than not.** When a game does not appear, run `npm run build` and grep `dist/cp/<slug>/index.html` before believing the page is broken; restart the preview server to clear it.
- **Browser state leaks between `javascript_tool` calls.** A failed batch may still have clicked half your test, so start each verification by clicking tab 0. Three "bugs" in this batch were only stale state.

**The `/cp/` pages carry a spoiler-masked table of contents, and it changes two things about verifying them.** `CpProblemLayout` renders a floating "สารบัญ" button (bottom-right) plus a panel, both `position:fixed`, built client-side from the page's `h2`s when there are at least 6. A plain TOC would defeat the whole reveal-after-hint design, because a heading like `เฉลย ตอนที่ 4 · สภาวะคงตัวมีรูปที่ตายตัวเสมอ` gives the answer away, so each entry whose section still holds a locked `.spoiler` shows only the part before the ` · ` separator followed by `…`, and a `MutationObserver` on every `.spoiler`'s class restores the full title the moment the reader opens that reveal. Consequences when checking a page: (a) **the centred-axis walk over `.panel`'s children must skip `.cptoc-fab` and `.cptoc-panel`** — they are children of `.panel` but `position:fixed`, so they are legitimately off-axis and are not a layout bug; (b) the scroll-position indicator on the button cannot be verified by scrolling in the preview pane, because the pane delivers neither wheel events nor `scroll` events for a programmatic `scrollTo` — dispatch `new Event('scroll')` after setting `window.scrollY` and assert the computed label instead. The panel is pinned with `left:1rem;right:1rem;max-width:22rem;margin-left:auto` rather than `width:min(...)`, because the latter overflowed the viewport by 1px at 375px.

**Two link styles coexist in `/cp/`, and any audit has to count both.** Pages link to each other as both `href="../slug/"` and `href="/cp/slug/"`. A scan written for only the relative form reported 6 pages with no outbound link and 5 with no inbound; counting both forms, the real figures are 3 and 1. Worse, a raw `grep` for a topic name over a `.astro` file counts hits inside frontmatter, comments, C++ code strings and SVG `<text>` labels, which is how one estimate of "13 links to add" collapsed to 2 after reading the actual sentences. When deciding whether a page needs a bridge: count only lines after the second `---` fence that are not inside `<text>` or inside a template string opened with `const … = `, then **read the sentence** — `/cp/archery` names the segment tree and binary search only to say neither one works there, so linking them would mislead.

**When a page tells a bug story, show the broken line, and prove the story first.** Five pages now ship a `<details class="expander">` inside their code section's `<Spoiler>` holding the broken snippet (with a Thai comment on the wrong line), the minimal failing input, and the wrong number beside the right one. Rules learned building them: compile both versions and **check whether the broken one really does pass the statement's samples**, because that is usually the story's central claim and it is not always true (`islands`, `pyramid-base`, `teleporters` and `archery` do pass; `sails` answers 15 against the true 10, and its expander says so); find the failing case by **exhaustive sweep over small inputs against the page's own brute force**, not random sampling, so you can claim the case is genuinely the smallest; and if the effect needs a page of setup to read, say so and ship nothing rather than forcing it. There is **no C++ compiler on Windows here** — use WSL Ubuntu's g++ 11.4.0 (`wsl -e bash -lc '…'`), working inside WSL's home rather than `/mnt/c`.

**The `/cp/` hub moves its filter rail onto `document.body`, and that is a standing hazard.** `.panel` carries an animation that leaves a `transform`, which would make it the containing block for a `position:fixed` child, so `src/pages/cp/index.astro` reparents the rail to `body` in side mode and puts a comment node back where it came from. Because `DivineLoreLayout` has a ClientRouter, leaving anything on `body` at swap time strands it on the **next** page. The bug that shipped: the `resize` listener that calls `layoutRail` was never removed, so after navigating away, any resize re-ran it with a detached rail and `appendChild`-ed the old hub's rail onto the problem page's body, unstyled and below the footer, once per hub visit (hence two copies). The fix is three-part and all three parts matter: `astro:before-swap` removes the resize listener, clears its pending timer, and restores the rail; and `layoutRail` returns early when its anchor comment is no longer `isConnected`. If you add anything else that reparents to `body` here, give it the same teardown.

**`IntersectionObserver` callbacks never fire in the preview pane, so do not build anything on it that you need to verify.** A control test observing an element sitting plainly inside the viewport produced no callback within 1.5 seconds, while `getBoundingClientRect` on the same element returned correct numbers. This is the same family as the pane not compositing frames. A visibility feature written with an observer therefore looks silently broken and cannot be told apart from a real bug. Prefer a geometry check inside a `scroll`/`resize` handler, which the pane *can* exercise: set `window.scrollY`, dispatch `new Event('scroll')`, then assert. That is how the table of contents' floating button learns to hide itself behind the prev/next card.

**Verifying a `/cp/` page (in addition to `npm run check`/`lint`/`build`)**
- **The preview pane often is not compositing frames**, which freezes every property that has a CSS `transition` at its old value. Colours read through `getComputedStyle` will lie (this produced one phantom "all the highlights are dead" report). Inject `*{transition:none !important}` before reading colours; layout metrics (`getBoundingClientRect`, `scrollLeft`, widths) stay trustworthy either way.
- Measure each player's table width across **every** step at a viewport ≥1500px — the width bugs are invisible on a narrow pane, where `max-width:100%` clamps them into looking stable.
- Walk every step and assert the numbers in the explanation match the numbers in the table, and that no source cell is highlighted while still showing `·`.
- Check the page at 375px: no horizontal page scroll, tables scroll inside their own card, and the active cell is scrolled into view.
- Grep the new page for em-dashes (must be 0) and zero-width spaces, same as `/knowledge`.

## Architecture notes

- **`astro.config.mjs`** sets `site` but no `base`, and relies on Astro's default `build.format: "directory"` output (e.g. `src/pages/knowledge/claude-intro.astro` → `/knowledge/claude-intro/index.html`; `src/pages/index.astro` still emits a flat `dist/index.html` at the root, same as before). GitHub Pages serves directory indexes natively, so links use `href="claude-intro/"` style paths, not `.html` suffixes.
- **`src/pages/index.astro`** is a standalone page — it does *not* wrap in `Layout.astro`, since the profile card's centered layout is fundamentally different from the two-column reading layout `Layout.astro` provides (no TOC, no donate button, no site footer). It renders its own `<ClientRouter />` and `<StarfieldBackground />` independently of `Layout.astro`, which does the same for every `/knowledge/*` page — both must keep doing so for View Transitions and the persisted canvas to work site-wide.
- **`src/components/StarfieldBackground.astro`** renders the `<canvas>` background shared by the home page and every knowledge page. It uses `transition:persist` so the same DOM node (and its running particle simulation) survives client-side navigation instead of being torn down and rebuilt: leaving `/` for a knowledge article scatters the stars outward and fades/pauses the canvas; returning reforms and fades it back in. All mutable animation state lives on the canvas node itself (`canvas.__starfield`), not in script closures, because closures aren't guaranteed to survive Astro's script re-execution on each swap — see the component for the `astro:page-load` + `data-bg` (`"interactive"` on `/`, `"plain"` on `Layout.astro`) lifecycle.
- **Emerald-star catch mini-game + clue hunt (in `StarfieldBackground.astro`).** A rare emerald star drifts across the upper sky on `/`; clicking it scores a catch, 6 catches = one "round"/trophy, difficulty ramps within a round (`SPEED_MAX_FACTOR`). All tunables are constants grouped at the top of the `<script>` (`GOLD_*`, `STAR_COLOR`, `ROUND_TARGET`, `TRAIL_MAX`, `ROUND_CELEBRATE_MS`, `CLUES`, …). **Two separate counters, deliberately different lifetimes:** `game.total` (session score shown in the HUD) is **in-memory only** — a full refresh resets it (chosen to reduce the hack surface, accepting lower UX). `progress` (completed-round count, 0..`PROGRESS_MAX`) **is persisted** via `localStorage` key `starfieldProgress` (load/save in the shared `src/lib/starClues.ts`); it drives the whispered clue ladder that teaches the hidden SecretConsole puzzle (Konami → `chi` username → anagram password), the re-openable "codex" panel (opened by the HUD trophy button), and the tier-10 worked-example reward. Neither counter is real security: editing `starfieldProgress` in storage only spoils your own clue hunt, and `/divine-lore/` still verifies its own token (`divineLoreToken.ts`) independently — so revealing clues never bypasses the actual gate. `SecretConsole.astro` reads `progress` (via `starClues.ts`) to add a gatekeeper acknowledgment line on `ACCESS GRANTED` for players who followed the stars. Any new interactive overlay here (the codex, like `.profile`/`.secret-console-overlay` before it) must be added to the black-hole `pointerdown` exclusion list.
- **`src/layouts/Layout.astro`** is the shared shell for all `/knowledge/*` pages (blue color theme, Sarabun font with fluid `clamp()`-based sizing controlled by the single `--scale` CSS variable, card/tag/breadcrumb/callout/references styling, a sticky "on this page" TOC auto-built from each page's `h2`s). New Astro content pages should use this layout via `<Layout title=... description=...>` rather than duplicating markup — see `src/pages/knowledge/claude-intro.astro` for the pattern. Layout also renders the prev/next article nav and the "last updated" footer itself, driven by the `prev`/`next`/`updated` props — don't hand-write a `<footer>` in article pages. The top-of-article header row (`.article-head`, holding the breadcrumb + `<ArticleByline>` publish/updated date at top-right) uses **CSS Grid**, not flex: `grid-template-columns:minmax(0, max-content) 1fr` (≥480px; single column below). The breadcrumb column prefers its one-line width but can shrink/wrap as a last resort; the date column (`1fr` + `text-align:right`) pins the date to the right edge and wraps it to two lines when space is tight (`ArticleByline` keeps each date `nowrap` and hides the " · " separator on wrap via a small script). **Don't try to make the breadcrumb never-wrap** — that reintroduces a long saga of the date overflowing the card / breadcrumb words dropping; a rare trailing-word wrap at extreme zoom is the deliberate, accepted tradeoff.
- **`src/data/articles.ts`** (typed `Article[]`) is the single source of truth for the knowledge article list (used by the listing page) and reading order (used by `getAdjacentArticles(href)` for prev/next links). `soon: true/false` marks placeholder ("เร็วๆ นี้") vs. published entries; only published entries count for prev/next. Each published entry also carries `dateISO` (YYYY-MM-DD publish date), optional `updatedISO` (YYYY-MM-DD), and `readingMinutes` (all optional so `soon` placeholders can omit them). Thai display strings are derived via `formatThaiDate`/`formatThaiDateShort` in `src/lib/dates.ts` — never store hand-written Thai date strings in the array. `getArticle(href)` looks up a single entry by href.
- **The `/knowledge` listing (`src/pages/knowledge/index.astro`)** groups cards by `tag` (preserving array order, so first-seen tag = section order: intro → Claude Code → มุมมอง) under a category header with a count, instead of repeating the tag pill on every card. Each card shows the title, desc, and a meta row (`อ่าน N นาที` + short date via `formatThaiDateShort(a.dateISO)` from `src/lib/dates.ts`) plus a hover "อ่านต่อ" chevron. Design rationale is research-backed (scannability / F-pattern / visual hierarchy). Slash-command tokens in `title`/`desc` render as code chips via the in-file `splitCommands`/`isCommand` helpers (see the slash-chip bullet below).
- **Slash-command tokens render as inline-code chips everywhere a title/description appears:** the article `<h1>` and breadcrumb (hand-wrapped in `<code>` in the page file), the `/knowledge` listing card title+desc (auto via `splitCommands`/`isCommand`), and the OG card (auto-detected in `card.ts`). Styling lives with each context — `.breadcrumb code` / `h1 code` in `Layout.astro`'s global `<style>`, `.item h3 code`/`.item p code` scoped in the listing. The breadcrumb chip also opts out of the breadcrumb's `text-transform:uppercase`/`letter-spacing` so the command reads literally (`/grill-me`, not `/GRILL-ME`). Facebook's share title is plain `<title>` text and can't be chip-formatted — that's expected, leave it.
- **Open Graph share cards are generated at build** by `src/pages/og/[slug].png.ts` (endpoint) + `src/og/card.ts` (renderer). Every `/knowledge/*` page's `og:image` is auto-derived in `Layout.astro` from the pathname (`/og/<slug>.png`); the endpoint renders one 1200×630 branded PNG per published article (read from `articles.ts`) plus one for the `/knowledge` listing, showing the article `title` + `tag` on the site's blue theme. Slash-command tokens in the title (words starting with `/`, e.g. `/grill-me`) are auto-detected and drawn as inline-code chips in JetBrains Mono. Fonts (`Sarabun-Bold.ttf`, `JetBrainsMono-Bold.ttf`) live in `src/og/` and are read at build (see the Thai-font gotcha below for why the rendering is set up the way it is). The `fb:app_id` meta tag in `Layout.astro` and `index.astro` is a **public** value (it appears in every page's HTML, so it needs no protection) — only a Facebook App *Secret* would be sensitive, and none is used here. **`/divine-lore/*` share cards** are a parallel setup: `src/pages/og/divine-lore/[slug].png.ts` renders one PNG per `divineLore.ts` entry via the same `renderCard` but with `theme: 'divine'` (emerald/dark vault palette + "· บันทึกลับ" footer — see the `THEMES` map in `card.ts`), and `DivineLoreLayout.astro` auto-emits the `og:`/`twitter:` meta (image `/og/divine-lore/<slug>.png`) **only when the page's slug matches a `divineLore.ts` entry** (so the gated listing gets none). These pages stay `noindex` — the OG tags are for link-sharing previews, which crawlers read regardless of noindex.
- **`src/pages/privacy.astro`** is the bilingual (TH/EN toggle via `data-lang` + `localStorage.privacyLang`) privacy policy, linked from the Layout site footer and the home page's fixed bottom-left `.privacy-link`. **Maintenance rule: any change to what the site stores client-side (new `localStorage`/`sessionStorage` key) or any new third-party request must be reflected in BOTH language blocks, and bump the "last updated" date.** Dates site-wide use CE years ("2026"), never พ.ศ. — a 2569 slipped in once. `src/pages/404.astro` is the branded not-found page (Astro emits `dist/404.html`, which GitHub Pages serves automatically for unknown URLs).
- **`src/data/socialLinks.ts`** (typed `SocialLink[]`) is the single source of truth for social profile URLs + their inline-SVG icon path data, consumed by `index.astro` (profile icons and the JSON-LD `sameAs` list) and `Layout.astro` (site footer, via the filtered `footerSocialLinks` export). All icons site-wide are inline SVGs — the Font Awesome CDN stylesheet was deliberately removed (it was render-blocking external CSS on every knowledge page); don't reintroduce an icon font for new icons.
- **`src/styles/fonts.css`** — self-hosted `@fontsource` imports (replaced the old Google Fonts `<link>`s). **Critical invariant: both `index.astro` and `Layout.astro` must import this same file**, so all `@font-face` rules land in one shared CSS chunk referenced by both page groups (verified in dist: one shared chunk with all 16 rules). This is the self-hosted successor to the old "same Google-Fonts URL on purpose" trick — same rationale: a single shared stylesheet means ClientRouter's `/` ↔ `/knowledge/*` swap never blocks on loading a new stylesheet. Intentional subsets: Sarabun latin+thai (body), Chakra Petch latin+thai (the mini-game HUD/clues/codex are Thai — don't drop the thai subset), Fira Code + JetBrains Mono latin-only (those families have **no** Thai subset; latin-only is correct there). Don't add new `@fontsource` packages without asking (see Conventions).
- **`src/pages/rss.xml.ts`** — RSS endpoint fed by `articles.ts` (published entries only, directory-style permalinks). The `<link rel="alternate" type="application/rss+xml" href="/rss.xml">` lives in both `Layout.astro` and `index.astro` heads. Declares `xmlns:atom` and emits an `<atom:link rel="self">` (via `customData`) so it passes W3C feed validation cleanly.
- **Cloudflare Web Analytics beacon** — a `<script is:inline … data-cf-beacon>` in both `Layout.astro` and `index.astro` heads. The token is a **public** value (like `fb:app_id`; it ships in every page's HTML, so needs no protection). `"spa": true` makes it count ClientRouter's pushState navigations, not just hard loads. Disclosed in `privacy.astro` (both TH+EN). `/divine-lore/*` pages never render this beacon at all (they don't use `Layout.astro` — see below), so there is no dashboard leakage to guard against there.
- **`src/pages/divine-lore/`** is the hidden area reached only via `SecretConsole.astro`'s solved-puzzle redirect (`window.location.href = '/divine-lore/'`, a full page load — never a client-side nav). `index.astro` is the **listing** (gated: checks the sessionStorage token from `divineLoreToken.ts` and redirects to `/` if invalid/missing) linking out to standalone secret-article pages (e.g. `global-workspace.astro`); **only the listing gates** — individual secret articles render unconditionally once linked, since the token check was never real security (see the comment in `divineLoreToken.ts`) and the owner wants the listing itself to be the one meaningful checkpoint. That matters: any script under this layout must wire on `astro:page-load` **and tear itself down on `astro:before-swap`**. A listener left on `window` survives the swap along with its closure over the old page's elements, and the hub's rail-layout code shipped exactly that bug (see the `/cp/` hub note below). This file previously claimed the layout had no ClientRouter, which sent one debugging session down the wrong path entirely. Listing entries live in `src/data/divineLore.ts` (mirrors `articles.ts`'s shape, minus `soon`/prev-next since entries are standalone drops, not a read-in-order series). To add a new secret entry: add it to `divineLore.ts` and create `<slug>.astro` under `src/pages/divine-lore/` using `DivineLoreLayout` — no gate script needed on the new page itself.

## Conventions

- **Reduced motion**: any new CSS/JS animation needs a `@media (prefers-reduced-motion: reduce)` fallback (instant state change, no transition) — see `profile.css` and `StarfieldBackground.astro`.
- **Hover vs. touch branching**: use `@media (hover: hover)` / `@media (hover: none)` to detect whether the primary input can hover, not touch-event feature detection (`ontouchstart` etc.) — handles hybrid touchscreen laptops correctly. Existing usages: `DonateButton.astro`, `profile.css`.
- **Accessible show/hide**: elements that must stay reachable by keyboard/tab order and screen readers (e.g. `.featured-link`) are hidden via `opacity`/`max-height`/`pointer-events`, never `display: none` or `visibility: hidden`. `display: none` is still fine for purely decorative icon-swap toggles (e.g. copy/check icon states in `CodeBlock.astro`/`DonateButton.astro`/`ShareButtons.astro`) where nothing needs to stay perceivable either way.
- **Never use `any` — anywhere, and never silently.** This is a hard rule across the whole codebase (`.ts`, `.astro` frontmatter, and `<script>` blocks), not just script blocks. `@typescript-eslint/no-explicit-any` is on, and `tsconfig`'s strict `noImplicitAny` flags untyped function params in `<script>` blocks (the language server surfaces these even though `astro build`/`eslint` won't fail on implicit any). If you think a value genuinely needs `any`, **stop and ask the user first** — do not reach for it on your own. The typed alternatives, in order of preference: give the value a real type/interface; use `unknown` + a narrowing guard (e.g. `JSON.parse` returns `any`, so assign to `unknown` then validate with `Array.isArray` / a `w is string` type-predicate before use — see `index.astro`'s scramble init); or, when a value needs a custom property absent from its DOM/global type (`window.__flag`, `canvas.__starfield`), define a named intersection type (`type Foo = Window & { __flag?: boolean }`) and cast once into a local, never scattering `(x as any).prop`. Event handlers get typed params (`(e: MouseEvent)`), and narrow `EventTarget` via `e.target instanceof Element` rather than casting to `any`. See `StarfieldBackground.astro`'s `StarfieldCanvas`, `SelfXssWarning.astro`'s `WindowWithSelfXssFlag`, and `index.astro`'s fully-typed scramble/tilt scripts.
- **Don't add new npm dependencies without asking first**, even for tooling (e.g. `astro check` wants to install `@astrojs/check`/`typescript`) — confirm with the user before changing the dependency footprint.
- **UI changes get verified in a live browser** (via the preview tooling), not just `npm run build` — a clean build only proves the code compiles, not that the feature behaves correctly across navigations/interactions.
- **Wide inline-SVG diagrams need a `.dgm-scroll` wrapper, or they're unreadable on mobile.** A `figure.diagram` holding a `viewBox="0 0 720 …"` SVG scales down to ~262px inside the panel at a 375px viewport, which shrinks 11px label text to ~4px. Wrap the `<svg>` (not the `<figcaption>`, which should stay at panel width) in `<div class="dgm-scroll">` and add a scoped block: `.dgm-scroll{overflow-x:auto;}` plus `@media (max-width:640px){ .dgm-scroll svg{min-width:520px;} }` — the page itself then never scrolls horizontally, only the diagram does. Reference implementation: `src/pages/divine-lore/options-101.astro`. Older articles with wide diagrams (e.g. `global-workspace.astro`) predate this and haven't been retrofitted yet; do new ones this way, and only touch the old ones if the owner asks.
- **`.dgm-scroll` alone isn't enough on a phone — new diagrams use `<ZoomableDiagram>`.** Panning a 520px-wide SVG through a 340px window still loses the whole-picture view, so `src/components/ZoomableDiagram.astro` wraps the `.dgm-scroll` pattern and adds a small "ขยาย" button that opens the SVG in a full-screen lightbox (Esc / backdrop click / close button all dismiss, focus returns to the trigger, body scroll locked). Usage: `<ZoomableDiagram caption="…"><svg …></svg></ZoomableDiagram>` — it renders the `figure.diagram` + `figcaption` itself, so don't wrap it in another `<figure>` and don't re-declare `.dgm-scroll` CSS in the page. It clones the source SVG into the overlay at open time, so the SVG must be self-contained (inline `fill`/`font-size` attributes, no page-scoped CSS styling its innards). Reference implementation: `src/pages/divine-lore/options-101.astro`.
- **`/cp/*` centres everything on one axis, with visual objects wider than the text.** `CpProblemLayout` overrides `body .panel` (DivineLoreLayout's card) to `46rem`; at `min-width:72rem` the card grows to `min(71rem, calc(100vw - 4rem))`, i.e. just enough for the widest block (`66rem`) plus the card's padding, so the leftover space reads as page margin outside the card instead of emptiness inside it, and then three concentric widths, **all centred** (`margin-left:auto;margin-right:auto`), share one vertical axis: text at `46rem` (`p`, `ul`, `ol`, `h2`, `h3`, `.callout`, `details`, `hr.divider`, plus the page header — `.dl-nav`, `h1`, `.cp-meta`, and `p.tag` which is a shrink-to-fit pill so it needs `margin-left:max(0px, calc((100% - 46rem)/2))` instead of a max-width — and the same list under `.spoiler-body`); tables/players/formulas/code windows are `width:fit-content` with `66rem` as a *ceiling* (they hug their content and centre, so a short code sample or a 3-column table does not stretch across the page and blow its columns apart — `table.rec` also needs `width:auto` to stop filling its hugged figure); diagrams and `.bookgame` at `52rem` (their SVGs are `viewBox="0 0 720"`, so `66rem` scales them ~2x and the labels balloon). Inside a player, `table.rec` must stay `width:100%` (only `figure.tbl table.rec` gets `width:auto`): a player's card width is set by its Thai explanation panel, and **Thai has no inter-word spaces so a paragraph's `max-content` is the entire sentence on one line** — letting the table hug its own content then left a 488px hole beside it (card 1277, table 787). Any `width:fit-content` container holding Thai prose has this trap. `table.io` (the INPUT/OUTPUT sample) is the exception that keeps `width:100%` capped at `46rem`: its cells hold short numbers, so `fit-content` collapsed it to ~213px, and it reads as given data alongside the prose. Captions (`p.io-note`, `figure.tbl figcaption`) are centred at `40rem` because centred text over ~1000px is hard to read. Four rejected attempts, in order, each of which the owner flagged on sight: (a) full-bleed via negative margins made 11 blocks stick out 106px past the card's rounded border onto the page background; (b) prose centred inside a `64rem` card while tables spanned the full card, so the text sat inset with a 192px gutter either side, reading as "เอียงซ้าย"; (c) every left edge aligned (text and blocks both starting at the card's content edge) made the blocks read as pinned to the text column, "กลางแบบโดนทางซ้ายลิมิตไว้", even though they measured as exactly page-centred; (d) text left-aligned in the page-wide card put it hard against the left edge (84px) with ~690px empty on the right. The rule that finally read as balanced: **one centred axis, nothing left-aligned, wider things simply extend further out on both sides equally.** Only `/cp/*` is affected; `/divine-lore/*` still uses the vault's original `42rem`.
- **Heading sizes in a page-level `<style>` must stay under the layout's.** `DivineLoreLayout` sets `h2{font-size:1rem}` (plus a green left bar + uppercase), so a page adding its own `h3` has to go *below* that — `/cp/pick-books` shipped `h3{font-size:1.02rem}` for a while, i.e. an `h3` measurably larger than its `h2` (20.7px vs 20.3px), which no amount of colour makes read as a subheading. Give the `h3` a smaller size and a clearly smaller `margin-top` than the `h2`'s `2.25rem`, so it groups under its parent.
- **Numeric/muted table text needs a contrast check, not just a vibe check.** `table.rec td.num` and its `.dim` sublabels shipped at `#6b7690`, which is **4.12:1** on the vault's `#0b1220` — under WCAG AA's 4.5:1, and at 13.4px for the sublabels. The palette's muted greys are tuned for large/decorative use; for numbers that carry the argument use `#cdd6ea` (12.8:1) and keep a genuinely-faint placeholder (e.g. the `·` for an unreachable DP cell) at `#7b8397` (5.0:1) so it still passes while staying visibly quieter. Compute the ratio in the browser rather than eyeballing it.
- **A payoff/graph diagram must be readable by someone who doesn't already understand it.** Every axis gets a visible name (not just a faint corner label), the zero line is drawn and labelled, and the profit/loss zones are called out — a reader should never have to infer which direction is "good". When a percentage appears, state its base (`-100% ของค่าสัญญา 5 ดอลลาร์`), especially when two series with different bases sit in one figure. If a figure would need the reader to switch mental frames halfway through (two strategies with different starting positions), split it into two figures with a paragraph between them instead of overlaying them.
- **Numeric data tables use the `figure.tbl` + `table.amo` card pattern.** `DivineLoreLayout`/`Layout` style no `<table>` at all, so a bare table renders as unstyled text sitting flat on the panel. Wrap every data table in `<figure class="tbl">` (the figure itself carries `overflow-x:auto` + darker `background` + border + `box-shadow` + radius, so the table scrolls inside its own card and the page never scrolls horizontally) with `<table class="amo">`, a `<caption>` as the card's mono/uppercase header, and a `<figcaption>` **outside** the scroll region at card width. Numeric cells get `text-align:right` + `font-variant-numeric:tabular-nums` + `white-space:nowrap`; the first column stays left-aligned. Helper classes: `td.hot` (gold, for cost/interest), `td.cool` (emerald, for savings/principal), `tr.tie` (highlight a break-even row), and `table.amo.wide` for prose-heavy comparison tables (re-enables wrapping + left alignment + a `min-width` per cell). Reference implementation: `src/pages/divine-lore/rich-people-mortgage.astro`. This is the sibling of the contest-article `table.io` rule below; don't reuse `.io` for non-INPUT/OUTPUT data.
- **A derived number the reader can't reproduce gets an `<ExplainNumber>`.** `src/components/ExplainNumber.astro` renders a number with a dashed gold underline; clicking it opens a popover (a bottom sheet under 560px) holding the formula, the substituted values, and a sentence or two on why it's computed that way. Usage: `<ExplainNumber value={`${pct(x)}%`} title="213.8% ต่อปี มาจากไหน" html={EX.yearlyCompound} />` — **the body is an HTML string prop, never slot children** (see the truncation gotcha below; do not "simplify" it back to a slot). Keep the bodies in one `EX` object at the bottom of the frontmatter so the article's math footnotes read as a set, with the KaTeX calls hoisted into a `TEX` object above it. Rules of thumb: only where the derivation isn't already shown next to it (a table that works the number row by row needs no popover), only on the **first** occurrence of that number in the article, in prose and key table cells but **not inside SVG diagrams** (the popover would be clipped by the lightbox), and never on a number whose derivation is the article's closing reveal. Reference implementation: `forex-3d.astro` (13 of them).
- **Numbers in an article body get computed in the frontmatter, never typed by hand.** Any article whose argument rests on arithmetic (amortization schedules, payoff tables, growth projections) should define the model as small typed helpers in the `---` fence and render every figure from them, including the values interpolated into prose sentences and the `<rect>` heights/coordinates of a data-driven SVG chart. Reference implementation: `rich-people-mortgage.astro` (one `schedule()` function feeds the payment table, the three-way prepayment comparison, the 30-bar stacked chart, the crossover marker, and ~15 inline numbers in the prose). Two payoffs: a hand-typed number that contradicts the table can't happen, and `npm run check` type-checks the model. Cross-check the model once against a throwaway script in the scratchpad before writing the prose around it, and if the page also ships an interactive calculator, assert in the browser that its output matches that script exactly (including edge cases like a 0% return and clamping a dependent slider's `max`) — the two implementations drifting apart is the real risk.
- **Contest-problem articles (`tag: 'เฉลยโจทย์แข่ง'`): sample tables + year-in-slug.** Every INPUT/OUTPUT sample table is `<table class="io">` with a `<caption>EXAMPLE</caption>` header and monospace cells with `letter-spacing` (so adjacent `<`/`>` don't crush together), styled as a distinct card (darker `background` + border + `box-shadow`) that clearly stands off the page background — see `icpc-warmup-2026.astro`'s `<style>` for the reference rules to copy. And the slug/`href` must carry the edition **year** (`icpc-warmup-2026/`, not `icpc-warmup/`) since these recur every year — same rule for any future event/edition-specific page.
- **Contest-problem articles: reveal-after-hint order + blur-spoiler are the standard — do this for EVERY problem.** Information is a DAG: give facts before reasoning (this is also in `edit-article/SKILL.md`). Per problem the reading order is: story → spec callout (input/constraints/output) → hint callout (end it on the question the reader should now be asking, e.g. "จะปักตรงไหนดี?") → *(optional but encouraged)* an interactive "ลองเอง" playground so the reader can discover the answer before reading it (see A's `needle-sim` in `icpc-warmup-2026.astro` — drag/auto-animate, own scoped CSS + a self-contained `<script>` init'd via `.class` querySelector, `prefers-reduced-motion` aware, keyboard/`role="slider"` accessible) → a short warm bridge line (`.ns-cue`, e.g. "ลองเล่นดูก่อนนะครับ พอมีคำตอบในใจแล้ว ค่อยไปดูเฉลย") → **the reveal, blurred**. **Everything that reads as the answer/derivation gets wrapped in a blur-spoiler** so it isn't seen until the reader taps to open it: the solution diagrams, the formula/"สูตร"/"หัวใจ" callouts, the derivation paragraphs, and any proof expander. Do NOT blur: the story, spec, hint, a diagram the hint explicitly points at ("ดูภาพข้างล่าง" stays with the hint), the INPUT/OUTPUT example tables (given data, not the answer), or the code expander (already collapsed behind its own `<details>`). Wrap markup: `<div class="spoiler locked" data-spoiler><button type="button" class="spoiler-reveal" aria-expanded="false">แตะเพื่อดูเฉลย</button><div class="spoiler-body"> …reveal… </div></div>`. The generic `[data-spoiler]` toggler script (removes `locked`, sets `aria-expanded`) and the `.spoiler`/`.spoiler-body`/`.spoiler-reveal` CSS already live in `icpc-warmup-2026.astro` — copy them for a new contest article. **No emoji/icons on the reveal button** (owner's hard rule — a decorative eye glyph was added once and removed).
- **Contest-problem articles: one tap unlocks EVERY blurred region in that problem — including the spoiler-y `io-note` under the example table.** The `<p class="io-note">` beneath an INPUT/OUTPUT table often works the given example and leaks the method (e.g. "min(10÷3,…)=3"). That must be blurred too, but the example table itself between the reveal and the note must stay visible — so it can't be one contiguous spoiler. Pattern: give the *main* reveal the button (`data-spoiler` + `.spoiler-reveal`); wrap each downstream spoiler-y block in a **buttonless** linked spoiler `<div class="spoiler locked"><div class="spoiler-body"> …io-note (and any post-example gotcha callout) … </div></div>` (no `data-spoiler`, no button). The toggler, on click, unlocks its own box then walks `nextElementSibling` unlocking every `.spoiler` until it hits the problem's terminating `<hr>` / next `<h2>` — so a single tap at the top clears the reveal, the io-note, and any trailing gotcha callout at once. Only blur io-notes that actually leak the method; a neutral one ("ตัวอย่างสมมติเพื่อประกอบความเข้าใจ") stays visible.
- **The back-arrow in a `.dl-nav` header must point *up* to the section's listing, never sideways at a sibling page.** Every page under `/divine-lore/` and `/cp/` opens with a `.dl-nav` whose first link carries the `dl-nav-arrow` chevron, and that arrow is the only thing on the page that reads as "go back". It is a plain hardcoded link, not `history.back()`, so it must be true for *every* way the reader could have arrived. A page that is listed as its own entry in `divineLore.ts`/`cp.ts` can always be entered directly (from the listing, a bookmark, a shared link), so an arrow pointing at some other article claims "กลับ" and then delivers a page the reader has never seen. `bitcoin-v01-source.astro` shipped exactly that: its arrow said "กลับไปบทบิตคอยน์ตั้งแต่ศูนย์" and pointed at `../bitcoin-from-zero/`, and it was the only one of the ten vault pages doing it. The shape that is correct, and which `CpProblemLayout` already uses: the arrow goes to the listing (`../` for `/divine-lore/*`, `/cp/` for a problem page), and a related page becomes a **second, chevron-free link** beside it. Same rule for wording anywhere on the page: "กลับไปอ่าน X ต่อ" asserts the reader was already at X, so for a page with more than one entry path write it as a forward move ("อ่านบทหลัก X"). To audit the whole section in one pass: print the first `href` inside each page's `.dl-nav` and check that every one is the listing.
- **Verify cadence is the user's call — ask once per session, then hold to it.** Two modes: (a) *incremental* — run `npm run check` + `npm run lint` + browser verify after each change, or (b) *batch* — just edit and let the user eyeball it, deferring all compile/type/lint/browser checks to a single pass right before commit (to save tokens/time). At the start of a session where this matters, ask which they want; once they pick, follow that mode for the rest of the session without re-asking. Only revisit if the user changes their mind. A new session resets this — ask again, don't assume last session's choice.

## Gotchas learned the hard way

- **Never pass `null` as the state to `history.replaceState`/`pushState` on a page with `<ClientRouter />` — it silently breaks the browser's back button.** Astro's router keeps its own bookkeeping in `history.state` (`{index, scrollX, scrollY}`, written on load), and its `popstate` handler treats a `null` state as "this entry isn't mine" and **returns without swapping the DOM**. The browser has already changed the URL by then, so the symptom is: the address bar says `/cp/` while the whole page is still the article you were reading, and pressing back a second time appears to skip a page entirely (it jumps to the entry before it, correctly rendered). Nothing errors, and `astro build`/`check`/`lint` are all green. This shipped in three places at once, the worst being `/cp/`'s filter-URL sync, which ran on *page load* (`apply()` calls `syncUrl()` at init), so back-from-any-problem was broken even with no filter applied. Always hand the current state straight back: `history.replaceState(history.state, '', newUrl)`. Diagnose by reading `JSON.stringify(history.state)` on the suspect page: a healthy entry shows `{"index":0,…}`, a broken one shows `null`. `replaceState` itself is still the right call for state that shouldn't create history entries (ten chip clicks must not become ten back-presses) — the bug is only the `null`.
- **`<script>` tags stop running after client-side navigation unless wired to `astro:page-load`.** With `<ClientRouter />` site-wide, top-level script code only ever executes once (ES module semantics) — after the router swaps in new DOM, any code that ran at the top level is now bound to detached elements. Wrap all init logic (querySelector, addEventListener, `new IntersectionObserver`, etc.) in `document.addEventListener('astro:page-load', () => { ... })` instead of running it bare, in *every* component/page with a script, not just ones that feel "SPA-relevant." This bit `Layout.astro`'s TOC builder, `DonateButton`, `ShareButtons`, `CodeBlock`, and even `index.astro`'s own tilt/reveal/handle-scramble scripts — missed on the first pass and only caught by manually navigating back and forth in a live browser, not by `astro build`.
  - Corollary: if you create a new `IntersectionObserver` (or similar) inside an `astro:page-load` handler, `.disconnect()` the previous one first — otherwise every navigation back to that page leaks another observer watching stale/detached nodes.
- **State for a `transition:persist`-ed element must live on the DOM node itself, not in script closures.** Even though the node survives navigation, the inline `<script>`'s module-level variables are not guaranteed to. Pattern used here: `canvas.__starfield = {...}` holds all mutable animation state, and `astro:page-load` checks `canvas.__starfield` to decide "fresh boot" vs. "resume."
- **When refactoring a function that ends in `return { ... }` into one that needs to derive extra properties (e.g. via `Object.assign`), actually convert the `return` into a `const x = { ... }` assignment.** Once, mid-refactor, the original `return { ... };` was left in place after adding an `Object.assign(...)` line after it — the new code became unreachable dead code with zero console errors (nothing threw, it just silently never ran). `astro build` and TypeScript didn't catch it either, since it's valid-but-dead code. Caught only via live browser testing that asserted on actual runtime state (e.g. checking a property existed on the object) rather than just "no errors in the console." Lesson: after any non-trivial refactor of stateful init code, verify the *new* behavior actually executes — absence of errors is not evidence of correctness for dead code.
- **Any new interactive overlay/UI on `/` must be excluded from StarfieldBackground's black-hole `pointerdown` handler and from profile.css's body-wide `user-select: none`.** The handler calls `e.preventDefault()` on every pointerdown outside `.profile` (to stop the drag from starting a native selection), which silently breaks placing the text caret with the mouse in any input rendered over it — no error, clicks just don't move the caret (bit SecretConsole's username/password fields). Fix both sides: add the overlay's class to the black-hole `pointerdown` exclusion list in `StarfieldBackground.astro` (the `closest('.profile, .secret-console-overlay, .gold-total, .gold-codex, .privacy-link')` call — grow that list), and set `user-select: text` on text inputs inside it. Even a plain link needs the exclusion: pointerdown outside it engages the black hole, so clicking would detonate a shockwave under the element. Related: toggling an `<input>`'s `type` (password↔text) resets its caret to the start — capture `selectionStart/End` before the switch and `setSelectionRange` after, and `preventDefault()` the toggle button's `mousedown` so it doesn't steal focus.
- **`preview_screenshot` times out (~30s) on this Windows box even when the page is perfectly healthy** — evals respond instantly, console is clean, and pausing the starfield rAF loop does not help; it's the capture tool, not the site. Don't retry more than once and don't treat it as a page bug. Verify with `preview_eval` (runtime state), `preview_inspect` (computed styles), and `preview_snapshot` (structure/text) instead — they cover everything a screenshot would and more precisely.
- **Driving pointer-based UI from `preview_eval` needs two workarounds.** (1) Synthetic `PointerEvent`s carry a `pointerId` that doesn't exist, so any handler calling `setPointerCapture` throws `NotFoundError` and silently aborts mid-handler (bit the scrubber test) — stub it first: `el.setPointerCapture = () => {}`. (2) `preview_click` on a link + an immediate `preview_eval` races the ClientRouter navigation — the eval can read the *old* page's `location`/DOM; re-check in a follow-up eval (or `element.click()` in one eval, assert in the next) before concluding navigation failed.
- **JSX comments `{/* ... */}` can't be a sibling of the single element returned from a `.map()` arrow** (`items.map((a) => ( {/* boom */} <a>...</a> ))`) — `astro check` fails with a cryptic cascade of `ts(1128) Declaration or statement expected` pointing at the end of the file, nowhere near the comment. Put template comments where children are allowed (e.g. just inside the parent container, above the `{items.map(...)}` expression).
- **When editing Thai copy, check for smuggled zero-width spaces before committing** — a U+200B slipped into a privacy-page edit once and is invisible in every editor. `Grep pattern '\x{200B}'` over the touched files catches it.
- **Reading a computed style through a CSS `transition` in a preview tab gives you a stale mid-flight value, not the target.** The browser pane often isn't compositing frames (same root cause as the `preview_screenshot` timeout below), so a transition that started never advances, and `getComputedStyle(el).color` keeps returning the *old* value forever. This nearly produced a false "the CSS fix didn't apply" report on the `/cp/pick-books` DP-table player, where `.dpsim td.num` has `transition:color .15s`: the CSSOM walk found zero matching rules (Vite dev uses `adoptedStyleSheets`, and even in `dist` the pane wouldn't expose `cssRules`), and the computed color disagreed with a `dist` CSS file that was textually correct. Before asserting on any transitioned property, inject `<style>SELECTOR{transition:none!important}</style>`, then read, then remove it. If you also need to prove a selector wins the cascade, probe with an `!important` rule on the exact selector: if the probe takes effect, the selector matches and the cascade is fine, so the disagreement is in your measurement.
  - Corollary: don't diagnose specificity by walking `document.styleSheets` in this pane — it can legitimately return no rules. Grep the built CSS in `dist/_astro/*.css` instead, and remember Astro turns `.a .b` into `.a[data-astro-cid-X] .b[data-astro-cid-X]`, so **every scoped compound gains an attribute selector's worth of specificity** and a rule meant to override another must add a real extra class, not just be written later.
- **Verifying rAF-driven canvas animation in a preview tab: don't wait for real frames — step the simulation manually.** Browsers throttle `requestAnimationFrame` in backgrounded/preview tabs, so "reload, wait N seconds, screenshot" is flaky and can assert against a stale frame. The starfield exposes its full state (including `tickFrame(t)`) on the canvas node as `canvas.__starfield`; drive it deterministically from `preview_eval` by calling `tickFrame` with synthetic timestamps, then assert on runtime state (particle positions/velocities/flags) or wrap the 2D-context draw methods with a spy to check what was actually drawn. Screenshots are for final visual confirmation only, not for verifying behavior.
- **Ambient particle drift must be a smooth arc, not per-frame random jitter.** Randomly re-aiming a particle's velocity every frame reads as buzzing insects/fireflies, not celestial bodies. The pattern that looks right: give each particle a constant slow speed and a small fixed per-frame turn rate so its path curves gently (see `DRIFT_SPEED_MIN`/`DRIFT_SPEED_RANGE`/`DRIFT_TURN_MAX` in `StarfieldBackground.astro`). Randomness belongs in the initial parameters (speed, heading, turn direction), not in the per-frame update.
- **A page cannot style *through* a wrapper that a component authored — the two carry different `data-astro-cid-*` values, and the selector silently never matches.** Sibling of the `createElement` gotcha below, but it bites even when every element exists in the template. When a page passes markup into a component's `<slot>` (e.g. a table into `CpStepPlayer`), the wrapper (`.dpsim`) gets the **component's** cid while the slotted table keeps the **page's** cid. A page-scoped rule written `.dpsim table.rec{…}` compiles to require the page's cid on `.dpsim` too, so it matches nothing: no build error, no console error, `npm run check`/`lint`/`build` all green, and the style just isn't there. This cost two failed fix attempts on `/cp/archery`'s player before `getComputedStyle` showed `table-layout` still `auto` after the rule had supposedly been written twice. **Diagnose** by reading the cid attributes off both elements (`[...el.attributes].map(a => a.name)`) — two different `data-astro-cid-*` values is the tell — and by checking the property through `getComputedStyle` rather than trusting that the rule was written. **Fix** by giving the page-authored element its own class and targeting that class directly (`table.rec.arcboard{…}`), never routing the selector through the component's wrapper. Watch for a second layer: the layout's own global rules (e.g. `body .panel .dpsim table.rec{width:100%}`) are longer selectors than a bare class, so an override may also need `!important` — which is legitimate here, with a comment saying which rule it is fighting.
- **Astro's scoped `<style>` blocks silently don't apply to elements created at runtime via `document.createElement`.** Astro scopes CSS by tagging template elements with a `data-astro-cid-*` attribute and rewriting selectors to require it; a `<div>` built and appended by a `<script>` (e.g. a log line in `SecretConsole.astro`) never gets that attribute, so a rule like `.log .log-denied { color: red }` compiles to effectively require the attribute on `.log-denied` too and never matches — no build error, no console error, the text is just always the default color. Fix: wrap the dynamic class in `:global(...)`, e.g. `.log :global(.log-denied) { color: red }`. Applies to any component that builds DOM nodes in JS and expects a scoped `<style>` block to color/style them.
- **Block elements passed as slot children to a component that sits inside a `<p>` silently truncate the page.** Astro's compiler parses the page as HTML, so a `<p>`/`<ul>`/`<div>` written between `<SomeComponent>` and `</SomeComponent>` closes the surrounding `<p>` (HTML's "a `<p>` can't contain a `<p>`" rule), and the stray closing tags cascade upward until they close the `<Layout>` itself. Everything after that point is emitted **after `</html>`** — the page loses its second half, with `astro check`, `eslint`, and `astro build` all green and no console error. Wrapping the children in `<template>` does **not** save you: browsers parse template content inertly, but Astro's compiler does not. This cost half of `forex-3d.astro`. The fix that is immune to it: have the component take the markup as an **HTML string prop** and `set:html` it into a `<template>` (see `ExplainNumber.astro`), so the compiler never parses that markup as page template. Detection: after adding any inline component, `node -e "const h=require('fs').readFileSync('dist/<page>/index.html','utf8');console.log(h.length - h.indexOf('</html>') - 7)"` — page-level `<script>` tags after `</html>` are normal Astro output, but any *markup* out there is this bug.
- **Nested template literals inside a `${...}` interpolation break Astro's frontmatter parser.** Writing ``const s = `${texBlock(String.raw`...`)}` `` in the `---` fence makes the compiler lose track of where the frontmatter ends; the symptom is bizarre and points nowhere near the cause — `astro check` reports `Cannot find name 'margin'` / `'color'` / `'display'` on every line of the page's `<style>` block (it is parsing the CSS as TypeScript), and `eslint` says `Parsing error: Unknown token at <EOF>, expected: "---"`. Fix: hoist the inner call into its own `const` first, then interpolate the plain identifier (see the `TEX` object above `EX` in `forex-3d.astro`). Same applies to `${arr.map((x) => `...`).join('')}` — build the joined string as a separate const.
- **JSX can't live in Astro frontmatter (the `---` fence) — only in the template below it.** A helper that *returns markup* (e.g. `const withChips = (t) => t.split(re).map((s) => <code>{s}</code>)`) defined in the frontmatter fails the build with a cryptic `Unterminated regular expression` (the compiler tries to parse `<code>` as TS and chokes on the following `/`), and `astro check` may not flag it. Keep frontmatter helpers pure data/logic (e.g. `splitCommands` returns a `string[]`, `isCommand` returns a `boolean`) and do the `<code>` wrapping inline in the template: `{splitCommands(a.title).map((seg) => isCommand(seg) ? <code>{seg}</code> : seg)}`. This also keeps scoped `<style>` working, since the `<code>` is authored in the component's own template. Bonus gotcha it caused: a build-only error invisible to `astro check` — always `npm run build`, not just `check`, after touching frontmatter that borders on JSX. `src/og/card.ts` rasterises an SVG of Thai+Latin text. Three approaches were tried and only the third works everywhere:
  1. sharp/librsvg with the font embedded as a base64 `@font-face` renders fine on the Windows dev box, but the **Linux CI's librsvg ignores the embedded font** — Thai comes out as `.notdef` boxes (Latin falls back to a system serif; Thai has no fallback and shows Unicode codepoint boxes). `astro build` is completely silent about it, so it only surfaces on the deployed site.
  2. `@resvg/resvg-js` loads fonts deterministically (explicit `fontBuffers`, `loadSystemFonts:false`) but its shaper **drops Thai mark-to-mark positioning** — tone marks stacked over an upper vowel (e.g. ไม้เอก over สระอี in "ที่") collapse onto the vowel and become invisible.
  3. **The working combo:** sharp/librsvg (its pango+harfbuzz stack shapes Thai correctly) + a generated **fontconfig** config. `card.ts` writes a `fonts.conf` pointing `<dir>` at `src/og/` and sets `FONTCONFIG_FILE` **before sharp is imported** (sharp is imported lazily inside `renderCard` for this reason), with a `<match>` that force-assigns every non-`JetBrains Mono` family to `Sarabun` so no system font can leak in for Latin — deterministic *and* correctly shaped.
